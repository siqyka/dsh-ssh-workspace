## 优化项

### O-01 失败重放不能以"有没有输出"判断副作用

**级别**：P0 · **复杂度**：M · **位置**：`lib/engine.js:754-787`、`lib/engine.js:609-632`

`exec` 只在"两次尝试都失败、且本次没有任何输出、不是超时也不是取消"时重放一次。注释把"无输出"当成"未执行"的证据，但这两件事并不等价：`rm -f x`、`touch x`、`git commit -q`、`mv`、一次成功的 `curl` 都可以静默完成。连接恰在退出状态返回前断开时，命令**已经执行**，重放会把副作用做第二遍。

`withSftp` 的问题形态相同但更宽：它按 `record.broken` 重放**整个回调**。文件系统回调不普遍幂等——单级 `mkdir` 已提交但响应丢失时会以 `EEXIST` 失败，上传会重复拷贝并重复触发进度。也就是说，当前的"重连一次"把传输层故障和业务语义混在了一起。

**建议**：把重试从"自动重放任意操作"改成"按操作类别决定"。

- 读类（`stat`、`lstat`、`readdir`、`read`）可重放，保持现状。
- 写类只允许**重试尚未发出任何字节**的步骤（例如连接建立、通道打开），一旦进入写入阶段就停止重放，向上返回明确的"结果未知"。
- 给 `exec` 增加显式的 `replay: 'safe' | 'never'`，默认 `never`；只有插件自己构造的只读探针才声明 `safe`。
- 失败结果里带 `outcome: 'unknown'`（而不是 `success: false`），让模型和用户知道"可能已经执行"，而不是误以为"没执行"。

**验收**：

1. 故障注入：命令执行完、退出状态丢失 → 远端只产生一次副作用，返回 `unknown`。
2. 上传在首个字节后断链 → 不自动重来，暂存文件被清理。
3. 读类操作断链仍能自动恢复，现有 `phase6` 与 `live` 的读路径不回归。


**推进结果（本轮）**：已修。`withSftp` 增加了显式的 `kind: 'read' | 'write'`（默认 `read`，保持既有读路径行为）；写类在传输断开后**不再重放**，而是关闭记录并把错误标记为 `outcome: 'unknown'`，同时记一条"连接在写入过程中断开，远端结果未知"的诊断。`exec` 的重放从"无输出即未执行"改为显式 `replay: 'safe'`，只有插件自己构造的只读探针（能力探测、`test -w`）声明它；其余命令一律报 `outcome: 'unknown'`，工具渲染出 `[outcome unknown]` 并明确提示"可能已在主机上完成，重跑前请先确认"。所有写类调用点（上传、下载、`putRemoteBytes`、`publish`、上传路由）都已标注 `kind: 'write'`。反向验证：还原旧行为后 4 条断言变红。

### O-02 推送式监视降级后，轮询句柄无人关闭

**级别**：P0 · **复杂度**：S · **位置**：`lib/remote-fs.js:789-819`

`inotifywait` 活着时返回的 close 只关闭 `closePush`。可这个 watcher 之后一旦断掉，`onError` 会重新启动轮询并写入 `closePoll`；此时调用方再 close，走的仍是"只关 closePush"的那条分支，**后来接替的轮询永远不会被关闭**。长时间开着编辑器、反复经历"推送掉线 → 轮询接替"，就会累积后台轮询、连接持有与定时器。

同一段还有一处静默：`startPolling()` 的 Promise 用 `running.then(..., () => {})` 吞掉了初始化失败，调用方无从知道降级没有成功。

**建议**：

- 用一份关闭状态替代两个并列句柄：`state = { mode: 'push' | 'poll', close?: Function }`，切换时先关旧句柄再赋新句柄；返回的 close 只关 `state.close`。
- 降级本身记 `degraded` 诊断（已有），但**初始化失败**要额外记一条并让 close 可重入。
- 加一个可断言的计数：同一 target 上的活动 watcher 恒 ≤ 1。

**验收**：模拟 `inotifywait` 在 5 秒后断开，close 之后不再有定时器、不再有进行中的 `withSftp`；连续 20 次"降级 → 关闭"后活动句柄为 0。（原文写的是 100 次；实测定为 20——每个周期要等两个真实轮询周期才能断言"没有轮询在跑"，100 次会把套件拖到一分钟以上，20 次已经能把"每次泄漏一个句柄"变成 20 个，足够证伪。）

**推进结果（本轮）**：已修。`watch()` 用**单一可变句柄** `live = { mode, close }` 取代了并列的 `closePush` / `closePoll`：安装新句柄时先关闭被替换的那个，返回的 close 关闭"当前那个"，降级时由 `install` 统一收口；若调用方在降级过程中就关闭了，迟到的轮询句柄会被 `install` 的 `closed` 守卫立即关掉，不再泄漏。轮询初始化失败不再被 `then(…, () => {})` 吞掉，会记一条 `degraded` 诊断。新增 `tests/watch-lifecycle-smoke.mjs`（8 项）：模拟推送掉线→降级→关闭、关闭与降级同 tick 竞速、连续 20 次循环，断言关闭后 2 个真实轮询周期内不再有 `withSftp` 调用。反向验证：还原旧的并列句柄结构后 3 条断言变红。

### O-03 原始字节上传绕开了 JSON 端点的 CSRF 前提

**级别**：P0 · **复杂度**：S · **位置**：`lib/routes.js:1153-1193`、`lib/routes.js:279-297`

其余 POST 端点共享的 `guard()` 有一个刻意设计的前提：**要求 `Content-Type: application/json`**。注释写得很清楚——跨站表单只能发 `text/plain` / `urlencoded` / `multipart`，而要求 JSON 会让浏览器先发一个本服务器从不批准的预检，于是"不需要 token 也能挡住 CSRF"。

`/upload` 是唯一一个接受**原始字节**的 POST：它自己实现了回环地址与 Host 头校验，却**不检查 `Content-Type`**（`lib/routes.js:1163-1170`）。这意味着一个跨站表单（`enctype="text/plain"`，或对回环地址的 `fetch`）只要目标浏览器能访问本机端口，就可能在不触发预检的情况下向该端点写字节。Host 头校验挡住了 DNS rebinding 那条路径，但这不等于挡住了"页面直接发向 127.0.0.1"的那条。

需要说清楚的是：**写入仍然受挂载根围栏与名称单段校验限制**，所以不是"任意路径写入"；但它是唯一一个能绕过既有 CSRF 前提的写端点，而这足以让攻击者把内容写进你正打开的工作区。

**建议**：

- 上传端点改成一个明确的非简单媒体类型（如 `application/octet-stream`）并要求它，跨站表单无法构造该类型；或继续用 `application/json` 承载元数据、另开一条要求自定义头（如 `X-DSH-Upload: 1`）的字节通道。
- 两条原始字节路由（upload / download）把"回环 + Host + method + 媒体类型"抽成一个 `guardRaw()`，与 `guard()` 并列而不是各自复制；让差异只有一处、可被测试点名。
- 补测试：模拟无 `Content-Type` 的 POST 与 `text/plain` 的 POST，断言 415/403 且**未写入任何字节**。

**验收**：跨站表单形状的请求无法写入；正常面板上传不受影响；`routes-smoke` 里有针对媒体类型的失败用例。

**推进结果（本轮）**：已修。新增与 `guard()` 并列的 `guardRaw()`，把"回环 + Host + method + 媒体类型"收成一处；`/upload` 现在**要求** `application/octet-stream`，`/download` 走同一守卫（GET 不检查媒体类型）。跨站表单无法构造该类型，`fetch` 设置它会触发本服务器从不批准的预检。`routes-smoke` 新增 15 项断言：缺 `Content-Type`、`text/plain`、`x-www-form-urlencoded`、`multipart`、`application/json` 五种形状一律 415，且断言 `state.opened === 0 && mkdirs.length === 0`（一个字节都没写、SFTP 都没到达）；同一请求带正确类型则成功，证明拒绝来自媒体类型而非夹具坏了。反向验证：去掉媒体类型检查后这 15 条全红。

### O-04 真实主机套件已经失效，却仍在文档里当作验收

**级别**：P0 · **复杂度**：S · **位置**：`tests/acceptance-smoke.mjs:217`、`tests/acceptance-smoke.mjs:114`、`tests/acceptance-smoke.mjs:220`、`tests/live-smoke.mjs:105`、`tests/live-smoke.mjs:335`、`docs/development.md:157-158`

`ssh_workspace_unmount` 的参数早已从 `deregister` 改为 `mode`，`acceptance-smoke` 仍传 `{ workspacePath, deregister: false }`，这条断言在任何真实主机上都会失败。也就是说，**"真机端到端"这一层目前是无声失效的**：平时它 SKIP，只有有人真的接上主机才会红，而文档仍把它当验收依据。

清理也有风险：`live-smoke` 与 `acceptance-smoke` 都对 `DSH_WS_TEST_DIR` 执行未加引号的 `rm -rf ${sandbox}`；`live-smoke` 的清理在 `finally` 里（这条没问题），`acceptance-smoke` 的清理在断言之后（`:220`），中途失败就不会执行，远端会留下临时目录。变量可配置而路径未加引号，一旦值里有空格或为空，删除目标就不是预期目录。

**建议**：

1. 修参数：改成 `{ workspacePath, mode: 'detach' }`，并断言 `mode` 回显。
2. 所有远端清理移进 `finally`，且删除前校验：路径必须是绝对路径、必须位于 `/tmp/` 之下、必须与默认前缀匹配；用 `shellQuote` 包裹。
3. 为空或不符合白名单时**拒绝删除**并打印原因，不做"尽力而为"的猜测。
4. 在 CI 里把"真机套件未运行"显式标成 SKIP 行并汇总，避免把 SKIP 当成 PASS 阅读。

**验收**：用一台一次性容器主机跑 `node tests/run.mjs live acceptance` 全绿；把 `DSH_WS_TEST_DIR` 设为空串 / 带空格路径时，套件拒绝执行删除并以非零退出，且远端目录未被触碰。

**推进结果（本轮）**：已修。`acceptance-smoke` 的 unmount 参数改为 `{ workspacePath, mode: 'detach' }`，并**断言回显** `mode` 与 `deregistered === false`——旧套件传 `deregister: false` 而参数早已改名，这条断言就是防止它再无声失效的哨兵。清理移进 `finally`（挂载成功才卸载、用插件自己的 `shellQuote`）。新增 `tests/scratch.mjs`：删除前校验"绝对路径 + 位于 `/tmp` 下 + 顶层目录以 `dsh-ssh-workspace` 开头"，不合格就**拒绝并打印原因**，不做尽力而为；两个真机套件都在创建任何目录**之前**先解析并校验 `DSH_WS_TEST_DIR`。新增 `tests/scratch-safety-smoke.mjs`（41 项，纯函数，无需主机）：空串、`/tmp`、`/`、`/etc`、相对路径、带换行、带空格等形状各有用例，并断言被拒绝时**一条远端命令都没发**。反向验证：让 `removeScratch` 信任任意路径后 7 条变红（含"对空串发出了 `rm -rf -- ''`"）。

### O-05 前台恢复后，后台重连成功回调可能不执行

**级别**：P1 · **复杂度**：S · **位置**：`lib/engine.js:382-394`、`lib/engine.js:496-497`

后台 attempt 调用 `acquire(alias, { background: true })`。如果用户在此期间已经手动触发过一次操作并成功建连，`acquire` 命中已有健康记录直接返回，`#backgroundConnect` 里的 `onReconnected` 就不会被调用——而已存端口转发的自动重开依赖这个回调。表现是"连接回来了，但保存的转发没有恢复"，且看不出原因。

**建议**：把"恢复动作"从"建连成功"里拆出来，按幂等语义挂在调度器成功路径上；或者在 `onReconnected` 前判断记录是否**本次新建**，新建才触发，否则也走一次幂等的 `restoreSavedForwards(alias)`（该操作本身已设计为幂等）。

**验收**：单测覆盖"前台先恢复、后台 attempt 后到"的时序，断言已存转发最终处于期望状态。

**推进结果（本轮）**：已修。恢复动作从"这次 attempt 建了连接"拆到调度器的**成功路径**：`onRestored` 在 `#fire` 与 `retryNow` 成功时都调用，`#backgroundConnect` 不再自己调 `onReconnected`。`reopenEnabled` 本身幂等（已存在的监听器直接跳过），所以重复调用安全。顺带补上了从未被调用的 `noteConnected`——`gave-up` 行现在会在真正连上后消失。`reconnect-smoke` 新增两组时序断言：前台先恢复、后台 attempt 命中健康记录（不拨号）时恢复仍执行；成功一次即不再 re-arm。

### O-06 持久 shell 的超时可能让下一条命令读到上一条的输出

**级别**：P1 · **复杂度**：M · **位置**：`lib/shell.js:68-105`、`lib/shell.js:143-160`、`lib/shell.js:246-272`

`run` 超时或取消后会清掉 `pending`，但远端命令仍在同一条 PTY 上继续跑；紧接着的 `run` 会立刻复用同一个会话，于是上一条命令的输出和结束标记可能混进下一条的采集窗口。命令自身的输出还可能被误判成后一条命令的结果。

同一模块里还有两处相关缺口：`#onData` 对每个 chunk 直接 `chunk.toString('utf8')`（`lib/shell.js:89`），一个多字节字符被切在 chunk 边界时会变成替换字符；同名 `open` 没有 single-flight（`:246-272`），并发打开同名会话会各建一条 PTY，后写覆盖先写、前一条失去引用。

**建议**：

- 会话内引入递增的 `generation`：超时后把该会话标记为"脏"，下一条 `run` 先发一个隔断标记并丢弃隔断之前的全部输出；或直接重建会话（成本更高但语义最干净，按 `timeoutMs` 的等级二选一）。
- `open` 按会话名做 single-flight，重复打开返回同一句柄并计数。
- 对跨块的多字节字符改用 `StringDecoder` 或按字节解析 ASCII 标记，避免中文输出被切半（这一点同样值得检查其它按块 `toString('utf8')` 的位置）。

**验收**：超时后立刻执行下一条命令，输出中不含上一条的任何行；并发 `open('default')` 断言只建立一条 PTY。

**推进结果（本轮）**：已修。会话内新增 `abandoned` 与 `generation`；超时或取消把会话标记为"需重新同步"，下一条 `run` 先发一个**隔断屏障**（只打印自己的 marker）并丢弃屏障之前的全部输出，因此上一条命令迟到的输出和它自己的 marker 都不会被当成新命令的结果。多字节解码改用 `StringDecoder`，被切在 chunk 边界的中文不再变成替换字符。`shell-smoke` 新增 5 项：超时后下一条命令只看到自己的输出与退出码、结果里不出现陈旧输出、写入次数证明屏障确实发生、CJK 被切两半仍还原。反向验证：去掉屏障后 3 条变红（结果里出现 `STALE-OUTPUT` 和旧 marker）；换回 `toString('utf8')` 后 2 条变红。

### O-07 传输的暂存名与背压

**级别**：P1 · **复杂度**：M · **位置**：`lib/transfer.js:133`、`lib/transfer.js:176`、`lib/routes.js:1130-1137`

暂存文件名是 `pid + Date.now().toString(36)`。同一进程、同一目标、同一毫秒内并发两次上传（面板连点、树上传与单文件上传并行），会共用同一个暂存路径并以 `'w'` 打开，可能交叉写入或在失败清理时删掉对方正在写的文件。下载侧 `out.once('drain')` 没有与 `error` 竞速，写流出错时等待可能一直挂着。

浏览器下载路由 `for await (const chunk of chunks) res.write(chunk)` 忽略了 `write()` 的返回值，也没有响应 `req` / `res` 的关闭。大文件在慢客户端下会把内核缓冲堆高，用户取消下载后远端读取也不会停。

**建议**：

- 暂存名加随机后缀与独占标志（`'wx'` 或 O_EXCL），冲突时重新生成而不是覆盖。
- 下载的 `drain` 等待与 `error` / `close` 用 `Promise.race` 统一，保证出错及时返回。
- 下载路由：`write()` 返回 false 时 `await once(res, 'drain')`，并在 `req.on('close')` 时中止远端读取；这对启用"大文件下载"的承诺是必要的。
- 长下载期间用 `engine.openChannel` 或显式 hold 固定连接，避免空闲回收器在中途摘连接。

**验收**：并发两次同目标上传，两个暂存名互不相同且最终内容正确；下载 1 GiB 文件时 RSS 有界，客户端中断后远端句柄在 1 秒内释放。

**推进结果（本轮）**：已修。暂存名抽成 `stagingNameOf(target, direction)`，在 `pid + 时间戳` 后加 16 位随机十六进制，并用 `wx`（O_EXCL）打开——随机避免碰撞，独占把罕见碰撞变成重试而不是相互覆盖。下载侧 `drain` 等待改为与 `error` 竞速，写流出错不再永久挂起。`/download` 循环改为尊重 `write()` 返回值的背压等待，并在 `req`/`res` 关闭时中止远端读取。`transfer-smoke` 新增 3 项：同一目标 200 次暂存名全部不同、命名带随机尾、下载暂存名也不碰撞；另加"写流出错时等待会被 `error` 结束而不是挂住"。反向验证：还原为仅时间戳后 3 条变红（200 次只剩 2 个不同值）。

### O-08 首次主机密钥落盘失败仍接受连接

**级别**：P1 · **复杂度**：S · **位置**：`lib/engine.js:459-480`

首次见到的密钥会写入 known_hosts；写失败时只 `logger.warn`，连接照常建立（`lib/engine.js:465-475`）。但本部署没有 console exporter，这条警告实际无人可见。用户会以为密钥已被固定，下一次连接却可能再次遇到"首次"，TOFU 的保证被悄悄削弱。

**建议**：落盘失败时把状态显式化为 `unverified` 诊断事件并在面板标出；安全优先的默认是**本次连接仍可建立但明确标记未固定**，若选择失败关闭，则必须给出可操作的恢复路径。无论哪种，都不得静默。

**验收**：把 `DSH_HOME` 指向只读目录，连接成功但状态面出现 `unverified`，且 diagnostics 可读。

**推进结果（本轮）**：已修。首次主机密钥写盘失败不再只 `logger.warn`（本部署无人读取）：记录一条 `degraded` 诊断（明确说明"未固定，下次连接会再次信任首次密钥"），并在引擎上维护 `unpinnedHostKeys`，由 `ssh_workspace_status` 输出 `unpinnedHostKeys` 与顶部 WARNING 行；后来成功固定时该警告自动清除。连接仍照常建立（拒绝连接比这个失败更糟）。为让安全关键路径可测，引擎加了 `verifierForTest` 接缝（`#connect` 内建 verifier 且同时开 socket，否则只能伪造 ssh2）。新增 `tests/host-key-smoke.mjs`（18 项）：接受、写入、指纹形状、未固定可见、诊断可读、清除、变更密钥仍拒绝。反向验证：去掉记录后 6 条变红。

### O-09 传输/元数据缺少 single-flight

**级别**：P2 · **复杂度**：S · **位置**：`lib/engine.js:647-668`、`lib/remote-fs.js`（缓存与列表段）

`streamChannel` 并发首读会各建一条第二 SFTP，只有最后一条被记录，其余失去引用且无法单独回收；元数据缓存同样没有进行中的合并，多条同目标 stat 会各发一次。对单用户不明显，多个消费者同时刷新面板与文件树时会放大延迟与连接数。

**建议**：缓存 Promise 而不是结果（进行中的 `load()` 直接复用，失败后删除条目以免把错误也缓存住）；`streamChannel` 用 `opening` Promise 做 single-flight，并保留"降级到共享通道"的现有语义。当前 `#cached`（`lib/remote-fs.js:861-874`）在 `await load()` 之间没有占位，正是并发重复请求的来源。

**验收**：并发 10 次首读只建立 1 条第二通道；并发同目标 stat 只发 1 次远端请求。

**推进结果（本轮）**：已修。元数据缓存改为缓存**进行中的 Promise**（而不是结果），并发同目标 stat 只发一次远端请求；失败的加载从缓存删除，避免把错误也缓存住。`streamChannel` 加 `streamOpening` single-flight，并发首读只开一条第二通道，失败时清空槽位以便重试（保留"降级到共享通道"语义）。`probe-smoke` 新增 5 项：三并发 stat 只 1 次加载、三个调用方都拿到值、失败不缓存、第二次重试成功。反向验证：还原为缓存结果后 1 条变红（3 次加载）。

### O-10 失败不总是可见：空列表与静默降级

**级别**：P1 · **复杂度**：M · **位置**：`lib/hosts.js:236-295`、`lib/routes.js:998`、`lib/client.js` 列表渲染段

`~/.ssh/config` 里暂不支持的条目、以及宿主存储读取失败，可能都表现为"列表为空"：`HostStore.rows()` 对不认识或不可用的条目一律 `catch { /* skipped */ }`（`lib/hosts.js:257-260`、`:280-283`），`#storeEntries()` 读取失败则返回 `[]`（`:288-295`）。用户看到的是"没有主机"，而不是"读不出来，原因是 X"，也就无从修复。

HTTP 处理器则常用 200 + `{ ok: false, error }`（如 `lib/routes.js:998`），前端需要逐处判读，与"参数错误用 4xx"的其它路由不一致。面板上已有多处降级（无 `rg`、无 `git`、无 `inotifywait`、推送掉线），但多数只在 diagnostics 里，用户看不到。

**建议**：

- 存储/配置读取失败与"确实为空"分开渲染：失败给出文件路径、错误码与重试入口；被跳过的条目至少给出"N 条未支持"的计数与原因摘要。
- 逐步统一错误契约：参数错误 4xx，服务端失败 5xx，业务性"做不了"才用 200 + `ok: false`；或者全部改为 HTTP 状态 + JSON 错误体，前端只判一处。
- 降级汇总成面板上的一行可展开提示（哪些能力缺失、影响到什么），而不是散落在日志里。

**验收**：配置文件损坏、目录不可读、主机条目不受支持三种情况各有可区分的界面文案；新增一个路由契约测试，断言错误状态码与前端分支一致。

**推进结果（本轮）**：已修，且修的过程中发现一个比原文更严重的问题。`HostStore.rows()` 改为 `listing()`，返回 `{ rows, skipped, storeError }`：被跳过的条目带原因、存储读取失败单独成字段；`rows()` 保留为裸列表兼容旧调用。HTTP 路由与 `ssh_workspace_hosts` 工具都返回 `skipped` / `storeError`，渲染时"空列表"与"读不出来"分开措辞。**顺带发现**：`ProxyJump` 在 ssh-config 块里是**字符串**，而 `needsProxyTransport` 只接受数组，于是 `ProxyJump bastion` 被判为"没有跳板机"，主机被列出并**直连目标**——既错误又不安全。已改为两种形状都接受（后续又补了 `Host *` 通配块与 `ProxyJump none`，见 O-10 的跳板机补丁）。新增 `tests/host-listing-smoke.mjs`（16 项）：真空、不可用条目、存储不可读三态可区分，跳板机条目被拒并带原因。

**第二轮补上漏掉的一半**：`storeError` 只保护了 entry store，`sshConfigAliases()` 里的 `readFileSync` 没有保护。一个不可读的 `~/.ssh/config`（路径被换成目录、权限问题、正在被替换的半成品文件）会**直接抛出 `listing()`**，绕开整条报告路径——这恰恰是 O-10 要消除的"空 vs 读不出来"，只做了一半。现在 config 读取失败也记进 `storeError`，且不覆盖 store 的错误（store 是主来源，报告第一个失败才是用户能行动的信息）。

对应的用例不再用 `chmod 000`：那在 Windows 上不产生不可读文件，只能跳过，而跳过在 CI 最常跑的平台上一无所证。改为把 config 路径做成**目录**，`readFileSync` 在哪个平台都以 `EISDIR` 失败，用例因此无条件运行。反向验证：去掉 config 读取保护后 3 条变红。`host-listing-smoke` 从 16 项涨到 32 项。

### O-11 可访问性：对话框与菜单

**级别**：P1 · **复杂度**：M · **位置**：`lib/client.js:1057`、`lib/client.js:2300-2322`、`lib/client.js:2271`

`aria-label`、`:focus-visible` 焦点环、Esc 关闭、菜单的 `role="menu"` / `role="menuitem"` 都已具备（`lib/client.js:2303-2309`），基础比一般插件好。仍缺的是对话框这一半：没有 `role="dialog"` / `aria-modal`，打开后不移动焦点、不做焦点陷阱，关闭后也不把焦点还给触发元素；菜单则只有语义角色，没有方向键 / Home / End 导航，也没有"打开后聚焦第一项"。对键盘与读屏用户，这几项决定"能不能用"，而不只是"好不好用"。

**建议**：抽一个最小的 `Dialog` / `Menu` 包装，集中处理焦点进入/返回、Esc、`aria-modal`、菜单方向键；不要在三处各写一遍。面板是往宿主 UI 上挂载的，焦点管理要容忍宿主自己的浮层（宿主若已有 dialog 基座，优先复用而不是另造）。

**验收**：纯键盘可完成"打开对话框 → 编辑 → 取消 → 焦点回到原按钮"；读屏能读出对话框名称与菜单项数量；菜单可用方向键走完所有项。

**推进结果（本轮）**：已修，分两次。**对话框**：抽出一个共享的 `useDialogA11y`——`role="dialog"` + `aria-modal` + `aria-labelledby` 指向标题；打开时把焦点移入第一个可聚焦控件、关闭时**归还给触发元素**（触发元素已消失则不强行归还）；Tab / Shift+Tab 在首尾环绕；Esc 在请求进行中**不生效**（避免 POST 继续而界面上什么都没有）。两个对话框都接同一个钩子，而不是各写一遍。

**菜单**（补做，第一次漏了）：新增 `useMenuKeyboard`——打开时聚焦第一项，`ArrowDown` / `ArrowUp` 环绕移动，`Home` / `End` 跳到首尾，跳过 `disabled` 项，`Tab` 关闭菜单而不是把焦点走丢到背后的页面。原推进结果只写了对话框，却把整条标成"已修"，而验收标准里明写"菜单可用方向键走完所有项"——这是记录与实现之间的偏差，已按实际补齐。

`client-shape-smoke` 共新增 27 项断言（对话框 10 项 + 菜单 17 项）。**菜单的方向键算术被抽成纯函数 `nextMenuIndex` 并在测试里真实执行**（12 个用例覆盖环绕、`current = -1` 入口、空列表、非导航键），而不是 grep 源码里有没有 `'ArrowDown'` 字样——后者无论环绕写没写对都会通过。反向验证五处，每处都真红：去掉 `ArrowDown` 环绕 → 1 条；破坏 `ArrowUp` 环绕与入口 → 2 条；去掉 `open` 门控 → 1 条；不排除 `disabled` 项 → 1 条；去掉焦点归属守卫 → 1 条。

### O-12 客户端单文件过大，建议绞杀式拆分

**级别**：P2 · **复杂度**：L · **位置**：`lib/client.js`（约 19 万字节）

样式、文案、多个对话框、主机编辑、文件浏览、转发面板都在一个文件里。它现在能工作，但每次改动都要在脑内维持一个很大的上下文；这也是 O-11 难以局部修复的原因。

**建议**：**不重写、不引入框架**。按现有渲染单元拆成同目录的多个模块（样式、图标、对话框基座、主机编辑、文件浏览、转发、持久会话），由 `client.js` 聚合导出，保持 bundle 入口不变。先拆最独立的对话框基座，再拆面板区。每次拆分后跑 `client-shape` 与手工冒烟。

**验收**：入口契约不变（`dsh.client` 指向的 bundle 可加载）；拆分是纯搬运，diff 中不出现行为变更。

**推进结果（本轮）**：本条建议的**前提不成立**，因此没有按原方案拆分。核对宿主实现（`app.asar` 内 `client-modules`）：

- `window.__ModuleLoader__.load({ id, factory })` 每个 `dsh.client` 入口只接受**一个** factory，没有同目录兄弟模块的加载路径；
- 要多文件就得声明第二个 `dsh.client` 入口，或引入构建步骤——两者都改变了宿主如何组装本插件，而"纯 loader、无构建"正是本包刻意保留的性质（O-12 自己也写着"不引入框架"）。

所以本轮做的是同一目标下的**可行子集**：在文件头加了一张"本文件地图"，按职责列出十个分节及其 banner 文本（行号只作参考，因为会漂移）。这让"编辑时要在脑内维持一个很大的上下文"变成"跳到对应的 banner"，而入口契约、无构建、单 bundle 三点全部不变。

**为什么不把"多入口"当选项**：上一轮把这件事描述成"需要你先决定是否引入构建步骤"，那是不准确的。多文件拆分并非"引入构建步骤的轻量替代"，而是**改变宿主如何看待这个包**——它从一个插件变成一组插件，`external` 图、`stripClientSuffix` 的 id 解析、每个入口各自的 factory 都要跟着变。这个代价与收益不成比例：真正的问题不是"文件大"，而是"改一处要在脑内维持 19 万字节"，而后者已被 banner 地图解决。因此本条**标记为不做**，而不是"部分处理"——后者会让下一轮再问一次。

**状态**：不做（受宿主入口契约限制；已用文件内导航缓解）。

|---|---|---|
| 1 | 无人操作时 socket 被硬断 → 后台循环自行启动 → 自动连回 | `client.on('close')` 真的会因外部原因触发 |
| 2 | 前台先把主机治好、后台 attempt 命中健康记录时，恢复钩子**仍然执行** | 恢复钩子接在"本次调用建了 socket"上就会漏（这是 O-05 的原始 bug） |
| 3 | `forget` 与空闲回收都**不**触发重连 | "断开"不能被写成"一直拨号" |
| 4 | 服务器换密钥 → 拒绝、阶梯终止、两个指纹都写进诊断 | 主机密钥路径此前只有单测桩（O-08） |

两个细节值得记下来：**硬断必须 `destroy()` 而不是 `end()`**——合盖或切网不发 FIN，优雅关闭测的是用户碰不到的路径；ssh2 的 `Connection` 只暴露 `end()`，真实 socket 要经 `_sock` 取。**换密钥必须重建监听器**——ssh2 在构造时把 `hostKeys` 解析进闭包，无法原地替换；重建恰好也是"主机被重装后同地址回来"的真实序列。

**条目 2、3 未做的理由（不是成本，是它们现在会红得没意义）**：

- **CI 矩阵**：`live` / `acceptance` 在 CI 里没有 `DSH_WS_TEST_ALIAS`，只会多出两个 SKIP 格子；Node 20 与 24 的差异若在无真实用例覆盖时出现，矩阵只是把同一批纯逻辑测试跑三遍。真正会红的差异在**文件系统语义**（`chmod 000` 在 Windows 上不产生不可读文件，所以"不可读存储"用例是用 `loadFails` 桩模拟的；只有 ssh-config 那条用了真实 `EISDIR`——把路径做成目录，在任何平台都以同样方式失败），而那是 Linux CI 才能验证的东西，不是 Node 版本。
- **真机双层清单**：需要一台容器主机与发布流程配合，属于运维决定。

若要最小可行矩阵，建议 **Ubuntu + Windows × Node 24 单一版本**，只跑 `lint` + `docs` + 纯套件：抓跨平台路径与换行，成本一个 workflow 文件。这需要先确认是否接受"矩阵只覆盖纯套件"这个前提，所以没有擅自加。

**状态**：条目 1、4 完成；条目 2、3 未做（附理由与最小可行方案）。

## 明确不做的事

写在这里，是为了避免下一轮讨论反复回到这些选项：

| 不做 | 原因 |
| --- | --- |
| 整体重写为 TypeScript / 引入构建框架 | 收益主要在类型与工具链，但会打断五个运行时补丁与 bundle 入口的现状；先做 O-12 的模块拆分即可获得大部分可维护性收益 |
| 自己实现 `~/.ssh/config` 的全部语义（Include / Match / 通配 / ProxyCommand） | 语义面大且易错，错误解析比不支持更危险；优先明确支持子集并**显式报告未支持项**（O-10） |
| 为远端命令实现"沙箱" | 远端进程的隔离需要远端内核能力，本插件的 SSH 通道跨不过去；假装沙箱比承认不隔离更危险。方向见 F-07 |
| 盲目加缓存 / 并发预取 | 当前瓶颈不在缓存命中率；在没有测量数据前加缓存只会让失效更难推理 |
| 承诺"断线后自动恢复正在运行的命令" | TCP 断链后远端进程的去向不可知；正确方向是把"结果未知"如实报告（O-01），而不是伪装成恢复 |

## Future

以下按"能力方向"组织，不承诺版本与时序。每项都写了前提与验证方式，避免变成愿望清单。

### F-01 断线语义：从"自动重连"到"可解释的恢复"

现状已经有后台指数退避重连、面板状态与降级诊断，这是很好的基础。下一步要解决的是**重连之后用户面对什么**：

- 远端进程在 TCP 断开后通常继续运行（取决于 nohup / 会话），插件无法知道；因此方向不是"替你恢复命令"，而是给出**明确的会话分代**：重连后新会话从新代开始，旧代标记为"已失效，可能仍在远端运行"。
- 工作目录、环境变量、持久 shell 的 cwd 可以尽力恢复（已知值就恢复），但必须标注"尽力"，不能声称等价。
- 变更监视在重连后要显式重建，并提示"离线期间的变更已重新扫描"（而不是假装从未掉线）。
- 面板上把"正在重连 / 已重试 N 次 / 下次时间 / 为何停止"落成一句话，现有 `retry` 字段已具备数据基础。

**前提**：O-01 与 O-05 先落地，否则"恢复"会把重放的副作用一起恢复。
**验证**：人为断网 30 秒再恢复，界面能说清"哪些还在、哪些不在了、哪些不知道"。

**推进结果（本轮，分代部分）**：会话分代已落地。`engine.generations` 记录每个 alias 的成功连接次数，且**存在 record 之外**——record 在每次重连时被替换，把代次只存在 record 上会永远回到 1。`generationOf()` 返回 `{generation, connected, since, previousLost}`，`describeGeneration()` 给出那句话：

- 第 1 代 → "connected (first generation)"，且**不**在面板与状态工具里多说一句（第 1 代是常态，每次都说就是噪音）；
- 第 2 代起 → "connected (generation N); anything started before the reconnect may still be running on the host"。

这句措辞在 `engine.js` 里只有一份，状态工具与 `/status` 都从它取，避免同一事实两种说法。反向验证：让 `describeGeneration` 把第 N 代也说成第 1 代 → 3 条变红；让 `generationOf` 从 record 而不是 map 读 → 2 条变红。

**推进结果（本轮，监视重建与起始目录）**：剩下两半做完了，其中一半做完才发现原条目问错了对象。

**变更监视在断线后不再永久停止。** 原来轮询失败一律 `changed(error)` 上报，而 seam 的契约是"给了 Error 就等于说我不干了，调用方请关闭"。这对健康链路上的权限错误是对的，对断线是灾难：轮询**因为**传输没了而失败，watcher 就此停掉，再没有人重启它。宿主也不会兜底——`dsh-client-ui-sidebar-files` 收到失败只标行、不重试，对 `watch-unsupported` 甚至静默吞掉，于是文件树悄悄冻结、一条提示都没有。

判定抽到 `lib/watch-recovery.js` 的纯函数里：**链路不通 且 有重连循环在跑**才重试；连接健康（是逻辑错，如路径没了、权限变了）或没人修（循环已 `gave-up`／没有循环）都照旧上报并停止。`startRemoteWatch` 断线时退避重试并只记一条"已暂停"；恢复后**无条件补一次重扫**——离线期间的快照无法证明什么都没变（同长度改写可能落在同一个 mtime 刻度里），静默跳过正是这次要消除的冻结。开头的首次观测也走同一策略（最多 5 次，约 31 秒），否则在断网时打开编辑器会得到一个从不存在的 watcher。

一个实测抓到的坑：第一次给重试计时器加了 `unref()`，`watch()` 在断网时直接挂住——这个计时器是唯一会唤醒调用方的东西，unref 之后进程可以带着未完成的 promise 退出。已改为不 unref 并写明理由。

**"环境变量尽力恢复"是伪需求。** 持久 shell 是 `sh -l`，新 shell 本来就会重新加载远端登录环境；所谓恢复环境变量，等价于"再开一个 shell"，而那正是已有的行为。真正的问题是 **cwd 被悄悄复位**：用户 `cd /var/log` 之后断线，下一次调用在新登录目录里执行，既不提示也没报错。现在按 key 记住**调用方指定的起始目录**（不假装知道远端当前目录——那读不回来），重连后按它重开，并在工具输出里把 `reopened` 与 `continued` 分开说：`reused: false` 同时覆盖"首次打开"和"断线后重开"，而只有后者丢了调用方以为还在的状态。`list()` 的字段叫 `startedIn` 而不是 `cwd`，因为后者会让人以为它跟踪 `cd`。

反向验证：`watch-recovery` 六个变异全红（去掉健康守卫 2、去掉"没人修"守卫 6、`gave-up` 算作在修 3、退避不增长 4、轮询改成上报 3、恢复后不重扫 1）；`shell` 五个变异全红（忽略记住的目录 1、重开报成首次 1、显式关闭仍记住 1、记住的覆盖显式 cwd 1、字段叫 `cwd` 2）。

### F-02 传输：可恢复、可校验、可取消

当前是"整文件 + 暂存 + rename"，对单文件足够，对真实项目不够：

- 断点续传（按已知远端大小与内容指纹续写暂存），并用 SHA-256 校验发布前的一致性；这需要远端有 `sha256sum` 或 `openssl`，缺失时降级为"仅大小校验"并说明。
- 目录下载与增量同步（现有上传树已具备基础），支持排除规则与并发上限。
- 传输任务化：进度、暂停、取消、失败重试各自有状态，面板能看到队列；取消必须真的中止远端读取（与 O-07 一并）。
- 冲突策略显式化：覆盖 / 跳过 / 重命名，默认不覆盖新文件。

**前提**：O-07 的背压与暂存唯一性。
**验证**：1 GiB 传输中途断网，恢复后只补传缺失分片且最终哈希一致；取消后远端不残留暂存文件。

### F-03 网络拓扑：跳板机、反向转发与多跳

- **跳板机**：`ssh2` 支持在已有连接上开转发通道，可据此实现 `ProxyJump` 语义（逐跳建连、逐跳校验 known_hosts）。不要用 `ProxyCommand` 执行任意本地命令——那会把"配置解析"变成"命令执行"。
- **反向 / 动态转发**：`ssh -R` 与 SOCKS 语义，对"远端访问本机服务"与"经主机出网"有用；需要配套的端口生命周期与面板管理（现已有正向转发的持久化经验可复用）。
- **多跳密钥与认证分离**：每跳独立认证策略，凭据不跨跳传递。

**前提**：hosts 配置模型要能表达"跳板链"，且 O-08 的密钥固定语义在每一跳都成立。
**验证**：两跳拓扑下端到端读写、转发、断开恢复均正确；每跳的 known_hosts 各自独立。

### F-04 主机配置：子集明确、错误可见

- 明确声明支持的 `~/.ssh/config` 子集，其余条目在面板上列为"未支持，原因是 X"，而不是静默丢弃（对应 O-10）。
- `Include` 与通配可以支持，但要有递归上限与循环检测；`Match` 先不做，明确拒绝。
- 主机分组 / 标签 / 搜索已有一点点（`tags` 出现在字段里），可以做成真正的组织能力：按环境分组、最近使用、只显示可达主机。
- 凭据来源扩展：`ssh-agent`（本地 socket 转发）优先于把私钥读进进程；系统钥匙串（Windows Credential Manager / macOS Keychain / libsecret）作为密码与口令的可选后端，避免自制加密成为唯一防线。
- 配置变更的即时生效：当前多处需要重连或重启，改为"编辑即失效缓存 + 下次操作生效"，并在状态里说明。

**验证**：构造一份包含 `Include`、通配、`Match`、不支持关键字的配置，面板逐条给出支持状态；`ssh-agent` 认证在无密码文件的情况下可用。

**推进结果（本轮，审计部分）**：新增 `lib/config-audit.js`，把"支持什么"从注释变成一张被检查的表。三种判定，且**不允许合并**：

| 判定 | 含义 | 例子 |
|---|---|---|
| `ignored` | 插件不读，也不会有功能缺失 | `ServerAliveInterval`、`ControlMaster`、`LogLevel` |
| `lost` | 插件不读，因此用户预期的功能不存在 | `LocalForward`、`CertificateFile` |
| `refused` | 无法履行，因此**拒绝该主机**而不是绕过它连接 | `ProxyCommand` |

（`Include` 与 `Match` 已从这张表里搬走：前者真的被跟随，后者按子集求值，见下一节。`ProxyJump` 也不再是 `refused`——它被实现了。）

`lost` 与 `ignored` 合并，正是"我的隧道从来没生效"变成无从追查的原因；`refused` 合并进 `ignored`，则是让主机绕过跳板机直连。

审计挂在 `HostStore.listing()` 的每一行上（字段 `unsupported`），因此面板、`ssh_workspace_hosts` 工具与诊断报告都从同一处取。匹配规则与 resolver 一致：**所有选中该 alias 的块**（含 `Host *`）、`!name` 排除、first-wins，且重复关键字只报一次并取第一个值。`ProxyJump` 不进审计——那个主机根本不会成为一行，它走 `skipped`，一处问题一处报告。

反向验证：把 `verdictFor` 让所有已知关键字都返回 `ignored` → 4 条变红；把通配匹配退化成精确比较 → 2 条变红；去掉去重 → 1 条变红。

**推进结果（本轮，`Include` 与 `Match`）**：两件原本写着"需要递归上限与循环检测"「先不做」的事，现在都做了，而做的过程中发现它们各自有一个比原描述更要紧的问题。

**`Include` 真正跟随**（`lib/include-chain.js`）。真实配置的写法是 `~/.ssh/config` 里几行、其余在 `conf.d/*.conf`；不跟随它，面板就是空的，而审计当时把这条报成 `lost`——文字没错，对用户无用。关键实现点是**就地插入而不是把被包含文件追加到末尾**：OpenSSH 的优先级是 first-value-wins 跨合并后的全文，追加会静默反转"哪一块先赢"。

环检测比的是**真实路径**，不是读到的字符串。这不是洁癖：同一个文件经 `conf.d/w` 和 `link/w`（指向同一目录的 junction/符号链接）被遇到两次时，字符串比较看不出重复，于是同一块被拼接两遍——而 first-wins 让第二份不改变任何结果，用户看到的只是"我按文档改了却没生效"。现在这种情况报 `duplicate`，真环报 `cycle`，两者分开是因为修复不一样。

写这条测试时踩了三次坑，都是同一个教训：**一个没有被任何变异弄红的用例，等于没写**。第一次用 `./self`——字面路径重复，两种实现都能抓到；第二次用硬链接——`realpathSync` 直接穿透，根本没造出第二条路径；第三次用环状 junction，但环长超过深度上限，两种实现都死在 `too-deep` 上。最后是"一个文件两种拼写"这个形状才真正区分开，而它也顺带查出了 sibling 重复这个真 bug（`onStack` 只能看见祖先，看不见兄弟）。

**`Match` 按子集求值**（`lib/match-eval.js`）。`host` / `originalhost` / `all` 可求值；`exec` **拒绝**——它会执行本地命令，而配置文件可能来自仓库；`user` / `address` / `port` / `final` 需要活连接，因此"选中无人"并说明原因。三种结果（不适用 / 拒绝 / 判断不了）不许合并，这正是 O-10 当年出事的形状。默认答案是"选中无人"而不是某个分支要记得加上。

一个必须说清的语义变化：`Match host web` **现在真的作用于 `web`**。旧测试断言它"必须不生效"，因为那时整个构造被忽略；那条断言保护的是"不要静默套用未求值的东西"，现在由"未求值的一律选中无人"继续保护。

**未做**：主机分组之外的"最近使用"、凭据后端扩展（系统钥匙串）。

### F-05 远端工作区：从"接管"到"原生能力"

这是最重要的一条长期方向。当前插件通过接管 `ctx.fs` / `ctx.shell` / `ctx.subprocess` / 投影 schema 来让宿主认识 `ssh://`，效果很好，但代价是每个宿主升级都可能打破某个补丁（O-15）。长期更健康的分工是：

- 上游提供"执行世界（execution world）"抽象：本地、容器、远端 SSH 作为同一接口的实现，插件退化为一个 provider。
- 在过渡期，把补丁面收敛成两个明确的 seam（文件系统 + 命令执行），其余（投影、终端、shell）尽量通过公开接口而不是内部符号。
- 多工作区并发与资源配额：每个主机连接数、通道数、并发传输数有上限并可观测。

**前提**：上游愿意接受该抽象；短期内通过 O-15 的契约测试降低升级破坏面。
**验证**：宿主升级后，插件在没有任何补丁的情况下仍能读写远端工作区（当前会显示 `probe: 'fixed'`，这正是已有的自退役信号）。

### F-06 能力探测与远程环境自检

- 探测范围从 `rg / git / inotifywait` 扩到终端相关（`$SHELL`、locale）与资源（磁盘余量、inotify 上限）。
- 形成"远程环境自检"一页：缺什么、影响哪个功能、如何安装（给出命令但不自动执行）。
- 不自动安装任何东西：在别人机器上安装软件是需要明确同意的动作。

**验证**：全新最小化容器上，自检能准确列出缺失项，且各项与实际功能表现一致。

**推进结果（本轮）**：探测从 3 项扩到 3 项工具 + 4 项环境事实，全部在**一次往返**里问完（`command -v` 扫描 + `$SHELL` / locale / `df` / `fs.inotify.max_user_watches`）。工具清单在 `lib/capabilities.js` 的一张表里（工具、依赖的功能、缺失的后果、安装提示），探测脚本的询问列表由这张表**派生**，所以加一项能力是加一行，而不是改四处渲染。

> **更正（2026-11-05）**：这里原本写"扩到 7 项工具"，其中 `sha256sum` / `tar` / `rsync` / `tput` 四条是**虚构的**。整套 `lib/` 里除能力表本身之外，这四个名字的引用数是 **0 / 0 / 0 / 1（仅一条注释）**——从未有一行代码调用它们。于是"缺 coreutils 就没有传输校验""缺 tar 就逐文件传输"这类说法描述的是两个状态里都不存在的功能：`lib/transfer.js` 从来没有算过任何哈希。
>
> 代价不是文字问题。`capabilities-report-smoke` 断言这四个"已加入探测"，而探测列表由表派生，所以这条断言**恒真**——它测的是循环，不是承诺。用户照提示装了 coreutils，什么也不会变，而面板会一直很自信地这么说。
>
> 现在这四条移进 `UNPROBED_CAPABILITIES`，每条带"为什么不探测"的理由；新增一条**直接读 `lib/`** 的断言：表里每一行声明的工具，必须在本文件之外真的被引用。反向验证：把 `rsync` 加回表 → 2 条变红。
>
> 剩下的三项（`rg` / `git` / `inotifywait`）是真实使用的，形态不变。

三个关键性质：

- **三态，不是两态**。探测不到 → `unknown`，不是"缺失"。把两者合并，会让一台连不上的主机被报成"什么工具都没有"。
- **只有 `absent` 带安装提示**。给 `unknown` 也加提示，等于请用户去装一个他可能早就有的东西。
- **`unknown` 不省略，也不装成"没问题"**。报告里它是独立一行。

环境事实各自是一条警告而不是判定：非 POSIX 登录 shell（csh / fish）、非 UTF-8 locale、可用磁盘低于 100 MB、inotify 上限过低。四条都写清了后果（例如 `ENOSPC`、替换字符、"大目录递归监视会撞上限"）。

**同时修掉一个真 bug**：原实现用 `stdout.includes('rg')` 判断存在，是整段输出的子串匹配——路径、locale 值里出现工具名就会误报为"已安装"。现在每条事实走独立前缀行（`dsh-tool:rg`）并整行匹配。反向验证：改回 `includes` → 2 条变红（含"值里出现 rg 不算存在"那条）。

**验证**：`tests/capabilities-report-smoke.mjs`（53 项，含新增的"承诺必须真的接线"一组）、`tests/capabilities-smoke.mjs`（19 项，已改为新格式）。界面在面板新增"远程环境自检"一节 + `GET /api/dsh-ssh-workspace/self-check`。

> **事后变更（2026-11-01）**：面板上那一节**已默认关闭**（`SHOW_SELF_CHECK_SECTION = false`），探测与 `GET /self-check` 保持不变，见 [ui.md](./ui.md) 的「自检分区默认关闭」。本节其余内容描述的是它打开时的形状。

**未做**：真正的"全新最小化容器"端到端验证需要真机，属于 O-14 剩下的真机清单。

### F-07 远端命令的"可审计"先于"可隔离"

不能假装有沙箱（见"不做的事"），但有可做的中间层：

- **审计**：每条远端命令记录命令摘要、时长、退出码、是否被模式门禁拒绝；敏感参数（密码、token）在写入前脱敏。
- **策略**：按主机 / 目录设置"命令需确认"的规则（例如 `sudo`、`rm -rf`、写系统目录），确认对话框展示完整命令与目标。
- **真正的隔离**：只有在远端明确具备 rootless 容器 / `bwrap` / `systemd-run` 等能力时才提供，并且必须在界面上写清"这是远端内核能力，不是本插件的保证"。

**验证**：审计记录能还原一次事故的完整链路；策略命中时命令未执行且用户能看懂原因。

**推进结果（本轮，审计部分）**：新增 `lib/audit.js` —— 一个与 `diagnostics.js` **并列**的有界环（容量 200，`seq` 在环外单调递增，所以能区分"丢了"与"重复"）。

为什么是两个环而不是一个：诊断环回答"哪里出了错"，命令环回答"这里到底发生了什么"。一次断网产生一串事件、零条命令；一次密集操作产生上百条命令、一条连接事件。共用一个环，任何一种都会把另一种挤出去。

记录内容：脱敏后的命令行、cwd（**独立字段**，不拼进命令行）、通道（exec / shell / terminal / background）、时长、退出码、是否超时、是否 `outcome: 'unknown'`、是否被模式门禁拒绝。

**脱敏在写入时发生，不在导出时**——只在边界脱敏的原始副本会从任何别的读者那里漏出去，而且没有"raw"开关可以留着不关。覆盖：`Authorization` 头（Bearer / Basic / Token 先于通用规则处理，否则通用规则的"一个词"会把 scheme 吃掉、留下 token）、`DB_PASSWORD=` 这类带前缀的赋值（`\b` 在 `_` 之后不生效，第一版就是这么漏的）、`--password` 之类的旗标、URL 里的 `token=` / `sig=`、家目录。反向验证：去掉 Authorization 规则 → 2 条变红；把赋值规则退化成只认 `password=` → 2 条变红。

**拒绝命令也记录**，且是唯一"确定没跑"的条目——日志在那里留空，读者无法区分"没跑"与"没记"。反向验证：去掉 exec 工具拒绝分支里的 `audit.record` → 1 条变红（该断言检查源码里确有这次调用）。

**未做**：策略层（按主机 / 目录的"命令需确认"，带完整命令与目标的确认对话框），以及真正的隔离。前者是产品决策（确认对话框的交互与默认值），后者按"明确不做的事"继续不做。

### F-08 界面与协作细节

- 文件浏览器：多选、批量下载、拖拽上传已有基础，可补"在远端打开终端 / 复制路径 / 设为工作区根"。
- 面板状态的一致性：所有"可能过期"的字段标明刷新时间与来源（实时 / 缓存 / 上次成功）。
- 国际化：目前中英词典已具备，新增文案要走同一注册表（已有 `locale-register` 套件守着，继续守）。
- 可访问性延续 O-11，并把焦点管理纳入截图回归或手工清单。

**验证**：键盘全流程可用；界面不出现"看起来是成功、其实是缓存"的状态。

**推进结果（本轮，状态来源标注）**：`/status` 的一次回复里混着三种年龄的事实——连接表是请求时读的，能力探测是可能比用户改主机更早的缓存，事件环按定义就是历史。三者用同一种方式渲染，等于隐含地声称它们是同时观测到的；"说已连接但文件树是空的"正是这种混合产出的矛盾。

现在每一节都带 `{kind, at}`：`live`（应答时从运行中的系统读取）、`cached`（存下来的结果，带**存入**时间而不是服务时间）、`stale`（刷新失败，只剩最后一次成功的值）。判定在**服务端**做，因为缓存有多老只有缓存所在的那一层知道；浏览器若自己从时间戳反推 TTL，两者会在第一次改 TTL 时分叉。面板只负责把它写成一句话。

三条不肯让步的细节：第四种 kind 会**抛**，而不是默默变成一个没人渲染的类型；时钟偏移导致的负年龄夹到 0（渲染成"未来"会被读成面板的 bug）；**从未探测**不算 `stale`——那会让人去找一场没发生的失败。能力一节的年龄取**最旧**的那一行，因为一节只和它最陈旧的那条一样新。

反向验证七个变异全红。其中一条最初是绿的，而且绿了两次：第一次断言只检查"调用存在"，于是把渲染改成 `false && …` 之后仍然通过；修好断言后，验证脚本又把 routes 套件整体当成"跳过"。后者暴露的是更普遍的问题——**部分跳过的套件曾被当作完全跳过**，而它恰恰是唯一跑着的那些断言。

### F-09 可观测性与诊断报告

- 诊断事件的稳定 schema（O-13）之后，可以生成"一键诊断报告"：版本、宿主版本、补丁探测状态、最近 N 条事件、脱敏后的相关配置片段。
- 不做自动上传；用户自己决定发给谁。这与 `SECURITY.md` 的立场一致。
- 性能基线：冷启动建连、首字节、1 GiB 传输、1000 文件目录列举、10 个工作区并发——先测量再优化，避免"凭感觉加缓存"。

**验证**：诊断报告能在不泄露凭据的前提下解释一次真实故障；性能基线有可重复的脚本与结果存档。

**推进结果（本轮，诊断报告部分）**：新增 `lib/support-bundle.js` + `GET /api/dsh-ssh-workspace/support-bundle`（`text/plain`，可直接在浏览器打开）+ 面板的"复制诊断报告"按钮。

它是**组装**而不是采集：每个字段都来自已有表面（主机列表、审计环、诊断环、探测缓存），所以诊断报告不可能报告面板会否认的事实。

一节一章，按读者需要的顺序：版本 → 补丁判定 → 主机（含 F-04 的配置审计）→ 工作区 → 连接（含 F-01 的代次）→ 端口转发 → 每主机自检 → 最近命令 → 最近事件。

脱敏规则与 `diagnostics.js` **同一套**（一个字符串两种掩码规则，是报告失去可关联性的开始）：alias 短写、家目录段打码、`root@host:22` 的登录用户打码而地址与端口保留。三个字符以内的 alias **整体打码**——`web` → `w*e` 只差一次猜测。

**过程中发现一个真实泄漏**：第一版把审计的 `exportText()` 输出整段嵌进去，而那段文本带着**未打码的 alias**（它是写给本地读者看的）。修法不是在导出时再脱敏一次，而是**从 rows 自己渲染**——脱敏必须发生在字符串**形成**的地方。反向验证：让 bundle 忽略 rows、退回预格式化文本 → 4 条变红；去掉登录用户打码 → 1 条变红。

**未做**：性能基线（冷启动、首字节、1 GiB 传输、1000 文件列举、10 工作区并发）。这需要真机与可重复的脚本存档，是运维侧的活。

**推进结果（本轮，判定与状态灯部分）**：报告是事实汇总，**从不给结论**——九个章节全是原始事实，没有一行说"这算不算问题"。这对粘贴是对的（它不能与面板矛盾），对面板是错的：用户不该需要知道阈值才能判断 `probe: 'fixed'` 意味着"该删了"、或者主机没出现在列表里意味着它的配置被拒绝了。

所以判定被拆成 `lib/diagnosis.js`，三态 `ok` / `warn` / `unknown` 且**不折叠成两色**——`unknown` 既不是绿也不是红，探测不到的主机不能报成"缺了它所有的工具"，也不能报成"一切正常"。聚合时**确定的坏压过不确定**：一个红点说"另外我还判断不了某件事"仍然是红点，可行动的那条事实更重要。

判定只读报告**已经在打印的字段**，不探测、不连接、不读文件，并在**服务端**计算（`/status` 的 `diagnosis`），浏览器只渲染——两处各自推导同一套规则，是"圆点与报告说法不一致"的开始。

**自检从判定里摘出来了（事后修正）**：第一版把缺工具与环境告警也算进 `findings`，于是装了干净 Debian、没装 `rg` 的机器上圆点直接变红。这正是本模块自己声称要避免的"太吵"——会变红的灯最终不被读，而一旦被忽略，它就再也不能承载真正要紧的那两条（未固定的密钥、读不出的存储）。现在自检只进 `notes`：仍在面板里（可展开）、仍在报告里（`advisory (not counted in the verdict):`）、仍在工具返回值里，但**不参与 `state` / `warn` / `unknown` 的计算**。分界线是"谁能改变它"：finding 是这个会话出了事（用户通常能在面板上处理），note 是那台主机就是这样（往往无 root、镜像受限，改不了）。看不见的降级仍然禁止，只是它不再冒充结论。

**判定要诚实，报告就得先带上它漏掉的事实**（全部来自已有数据，无新增采集）：新增 `## host keys` 一节（被接受却没能固定的密钥，是"报告什么都没说"与"报告说一切正常"曾是同一画面的地方）；被跳过的主机带原因列出（`~/.ssh/config` 里存在但无法使用的条目以前**根本不出现**，于是"我明明配了却用不了"没有线索）；连接代次大于 1 时说明"重连前启动的远端进程可能仍在运行"（"偶发断线"与"从没连上"以前在报告里长得一样）。另外空补丁列表不再把"补丁不需要装"和"我不知道补丁装没装"写成一句。

**反向验证**（每条都真红）：把 `broken` / `pending` 也算成问题 → 4 条变红（太吵，一个每次启动都红的灯没人看）；把 `fixed` 不再报 → 1 条红（太安静，这正是整个模块存在的理由）；把 `unknown` 折叠成 `ok` → 3 条红；把非零退出算成失败 → 1 条红；把 alias 塞进 `detail` 字符串 → 2 条红（脱敏必须发生在字符串形成处）；把自检挪回 `findings` → 2 条红；让聚合把 `notes` 也数进去 → 5 条红；去掉报告的 advisory 标题 → 2 条红。

| F-07 | 命令审计环，写入时脱敏，拒绝也记录 | 策略层（命令需确认）、真正隔离 |
| F-08 | 文件浏览器「复制路径 / 设为工作区根」、主机标签 UI、**状态来源标注**（live / cached / stale 三态），焦点管理已由 C-01 的 `useDialogA11y` 覆盖 | 「在远端任意子目录开终端」（宿主的 `terminal/create` 没有 cwd 参数，做不到） |
| F-09 | 诊断报告（组装、脱敏、可粘贴，不上传） | 性能基线 |

选择标准是：**能在不引入产品决策、不依赖真机的前提下把"说不清"变成"说得清"**。剩下的每一项都需要一个决定（恢复要做到多诚实、确认对话框怎么交互、是否引入构建步骤）或一台机器（真机验收、性能基线），所以它们没有被顺手做掉。

反向验证脚本 `scripts/reverse-verify-future.mjs` 对上述每一处都做了破坏性检验：14 个变异全部使对应套件变红。它不是 CI 的一部分，因为它会临时改写源文件——跑它是审阅动作，不是每次提交的动作。

## 判断依据与局限

- 本文所有 P0/P1 判断都能在源码里指到具体行；涉及"时序""可能"的，均给出了触发条件，未做真机验证。
- **没有性能数据**：文中所有性能相关建议都是结构性的（背压、single-flight、句柄上限），不是基于测量的瓶颈定位。真实瓶颈可能不同，F-09 的基线应先做。
- 子代理的复核扩大了覆盖面，但结论已逐条回读源码；凡不能复现的推测没有写入本文。已知未验证项：`dispose` 与在飞握手之间的竞态、`remote-fs` 轮询遇到传输错误后是否自愈、`fs-shim` 的 `open` 与空闲回收竞态、同一目标并发上传是否真的会撞同一毫秒——这些按"需要故障注入才能定性"处理，没有升级为正式条目。
- 未运行测试套件（初版只读），因此"套件通过"不是本文的论据；相反，O-04 指出其中一个套件当时并不可信（已修）。
- 本页已登记到 [docs/README.md](./README.md) 索引与两个根 README（推进完成后补的；初版按要求未登记）。
- Future 的四项推进结果同样**没有真机验证**：自检、配置审计、命令审计、诊断报告都在替身与合成输入下测过，真实主机的行为差异（尤其 `df -Pk` 在不同文件系统上的输出、`awk` 的可用性）可能不同。`unknown` 状态正是为这类差异留的退路。
