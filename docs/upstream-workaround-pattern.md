# 上游补丁的退役模式

> 定位：一套可复用的方法，用来管理「为了绕开宿主缺陷而存在的代码」——让它在宿主修好之后**自己停用、并主动要求被删除**，而不是变成没人敢动的历史包袱。
>
> 本页讲**模式**；本插件里唯一一个实例的完整登记见 [upstream-workarounds.md](./upstream-workarounds.md)。两页配合读：先看这里的规则，再看那里的实例。

## 问题：补丁的死亡方式决定了它的成本

绕开宿主缺陷的补丁有一个别的代码没有的性质：**它的正确结局是被删除**。插件在自己接缝上的接管随插件一起演进，那个是产品；而「等宿主修好后就不该存在」的代码，每多活一天都在制造两种成本：

| 成本 | 表现 |
| --- | --- |
| **读者成本** | 每次翻到这段代码都要重新判断「还需要吗」，而答案不在代码里 |
| **双重作用** | 宿主修好后补丁仍在跑，两层放宽叠在一起，行为不再可推理 |

常见的处理方式是注释里写一句 `// TODO: 等上游修了删掉`。那不是机制，那是愿望：它依赖某个未来的人恰好看到这行字、恰好记得判断、恰好有空。实际结局是这段代码活到项目结束。

**本页描述的模式的全部价值，就是把这个判断从「靠人记得」变成「由系统回答」。**

## 适用判定：什么时候需要这套东西

先判断这条改动到底该不该登记。判错会很贵——见最后一节的成本讨论。

| 情形 | 要不要登记 | 理由 |
| --- | --- | --- |
| 插件在宿主提供的接缝上接管行为（`ctx.fs` / `ctx.shell` / `ctx.subprocess` / 某个 registry） | **不要** | 这是插件存在的理由，没有「上游修好后该消失」的那一天 |
| 绕过宿主自身的缺陷，宿主一修就该消失 | **要** | 本页的全部内容 |
| 只是觉得宿主的某个行为可以更好 | 不要 | 那是产品决策，写进 issue 或 changelog，不是补丁 |
| 临时兼容某个特定版本 | **要**，但还要写死版本上限 | 否则它会在没有意义的版本上继续生效 |

还有一个经常被忽略的前置判断：**这条补丁失效时的表现是什么？**

- **用户可见的损坏**（会话打不开、数据错、功能整个消失）→ 值得付这套成本；
- **体验略差**（慢一点、提示不够友好、少一个便捷操作）→ 不值得。

这一条比机制本身更值得传播。本插件的 `UPSTREAM-1` 之所以配得上约 500 行模块加两个测试套件，是因为它失效时用户看到的是「历史加载失败」，而且报错完全指不向真正原因。同样体量的机制套在一个「提示文案不够好」的补丁上，就是纯粹的工程浪费。

## 一个模式的七件套

### 1. 可 grep 的稳定 id

形如 `UPSTREAM-<序号>-<包名>-<主题>`：

```
UPSTREAM-1-working-directory-isAbsolute
```

它必须同时出现在：代码框注里、登记文档里、CHANGELOG 里。这样 `grep -rn UPSTREAM-1 .` 就直接给出删除时需要触碰的**全部**位置——删除清单不再依赖某个人的记忆。

### 2. 缺陷原文 + 一行修法

登记里要写清**上游的原样代码**和**改完之后的样子**，而不是只写「上游有个 bug」。

```js
// 现在
const directorySchema = z.string().min(1).refine(isAbsolute).nullable()
// 修好之后
const directorySchema = z.string().min(1).refine((value) => isAbsolute(value)).nullable()
```

理由很实际：写这段的人是你，读这段的人是三个月后另一个人（或者你自己）。「上游有个 bug」不能帮他判断宿主到底修没修；两行代码的 diff 可以。

### 3. 探测**行为**，不要探测版本

这是整个模式里唯一无法被替代的一步，也是最容易被抄错的一步。

**探测版本要求你预先知道「哪个版本修好了」，而你在写补丁的那一刻不可能知道。** 上游还没修，那个版本号还不存在。你只能写「`>= 某个猜出来的数字`」，而猜错的两个方向都要付代价：猜高了，在仍有缺陷的版本上不装补丁，用户直接坏掉；猜低了，在修好的版本上继续装，等于双重放宽，而你以为它还在起作用。

**探测行为不需要任何关于未来的知识。** 拿到 schema，喂一个 `ssh://` 值，它接受了吗：

```js
// 宿主修好后的 schema 会接受它；有缺陷的那个会抛 Invalid input
schema.parse('ssh://upstream-probe/absolute/path')
```

上游修好那天，探测结果自动从 `false` 变成 `true`，代码里没有一个字需要维护。

一句话记法：**探测版本是在预测一个尚未发生的发布，探测行为是在观察一个已经存在的对象。前者是赌博，后者是测量。**

#### 3b. 但「行为变了」未必是上游改的

上面那段有个前提：**中间没有别人动过被探测的那个谓词**。一旦补丁自己也改了这个谓词（本插件的内建桥接就替换了 `node:path.isAbsolute`），接受就不再是干净证据：

| 谁改了 `isAbsolute` | schema 何时构造 | schema 接受 `ssh://` 吗 | 这说明上游修好了吗 |
| --- | --- | --- | --- |
| 没人 | — | 否 | — |
| 上游已修（读绑定） | 任意 | 是 | **是** |
| 我们的补丁 | 补丁**之后** | 是 | **否**——它捕获的是我们的函数 |

第三行在真实部署里不是边角情况：桥接在插件自己的 `apply()` 里装，`workingDirectory` 单元在服务首次被访问时才构造。于是 schema 捕获的**正好是补丁后的谓词**，探测报告 `fixed`，而源码里 `refine(isAbsolute)` 一个字没改。

**后果比误报本身严重**：`fixed` 打印的建议是「删掉它」，于是一个仍然承重的补丁被自己的探测器劝退。真实形态是：面板亮红灯、报告说「上游已修复，删掉这个 workaround」、而宿主源码仍是缺陷版本。

**判别式不是「接受了吗」，而是「它读了吗」**：探测期间把谓词换成一个一次性的记账包装，看 schema 是否**调用**了它。捕获了函数值的 schema 永远不碰这个属性。

```js
let read = false
const current = path.isAbsolute
path.isAbsolute = (v) => { read = true; return current(v) }   // 语义不变，只记账
const accepted = schema.parse(remote)
path.isAbsolute = current
// accepted && read  → 上游读绑定，真修好了
// accepted && !read → 捕获了我们的补丁，缺陷仍在
```

这条规则适用于**任何**自我退役探测：先问「探测值和我的补丁是否共享同一个可被替换的符号」，共享就必须用「读没读」而不是「变没变」。正负对照（下一节）挡不住这个错误——两个对照都不涉及「补丁先于构造」这一种顺序。


### 4. 探测要有正负对照

只断言「探测在坏 schema 上返回 false」是不够的：一个**恒假**的探测（比如 `typeof schema.parse !== 'function'` 写错成别的）也会通过这条断言，而它永远不会报告「已修复」。

必须同时断言：

- 负对照：**已知有缺陷**的对象上，探测返回 false（证明它真的能看出坏）；
- 正对照：**已知已修复**的对象上，探测返回 true（证明它真的能看出好）；
- **顺序对照**：补丁**先于**缺陷对象构造时，探测仍必须返回 false（第 3b 节那一行）。

第三条是 0.2.8 补上的。前两条都成立时，探测照样可能把「捕获了我们的补丁」误判成「上游修好了」，因为两个对照都不涉及桥接已经装好的那种顺序——而那正是生产的顺序。

`tests/projection-relax-smoke.mjs` 三个方向都有：`capturedSchema(originalIsAbsolute)` 是负对照，
`fixed` 那个 schema 是正对照，第 10 节的 `withBridge(...)` 是顺序对照。

### 5. 三态结论，不要布尔

**这是本页最重要的一条，也是本仓库在 0.2.7 里补上的真实缺陷。**

一个布尔 `needsWorkaround` 会把三件不同的事压成同一个值：

| 实际情况 | 布尔值 | 真实含义 |
| --- | --- | --- |
| 探测了，上游还没修 | `false` | 补丁仍承重，正常 |
| 探测了，上游已修 | `true` | 补丁可删，该通知人 |
| **没法探测**（宿主改了内部形状） | `false` | **什么都不知道** |

第三种是最坏的。它和第一种共享同一个 `false`，于是：补丁被静默跳过 → 用户重新遇到那个原始 bug → 而所有信号都显示「一切正常」。**失败形态和它要预防的那个 bug 一模一样，而且因为有「保护代码」存在，更难排查。**

所以探测的返回值必须是一个**封闭的状态集**：

| 状态 | 含义 | 需要谁做什么 |
| --- | --- | --- |
| `fixed` | 上游已修 | **通知人删掉补丁** |
| `broken` | 上游仍有缺陷 | 无需动作，补丁正常工作 |
| `pending` | 对象还没出现（重载 / 测试装配顺序） | 无需动作，拦截钩子会接住 |
| `already` | 本进程里另一次安装已经打过补丁 | 无需动作（防自我误判，见下） |
| `unprobeable` | **无法判断**（宿主的形状不符合预期） | **必须告警**，不能静默 |
| `disabled` | 操作者用环境变量关掉了 | 无需动作，但要在状态里可见 |

`unprobeable` 是整个模式的报警器。它存在的意义就是让第 3 种情况不再伪装成第 1 种。

### 6. 信号必须送到**人能看到**的地方

这一条同样来自真实踩坑。

`logger.info('patch is no longer needed')` 看起来完美：有语义、有级别、又不会吵。但在这套部署里，**它到不了任何人眼前**：

| 环节 | 事实 |
| --- | --- |
| 宿主装了什么 exporter | 没有 console exporter |
| `ctx.logger` 写到哪里 | 一个环形缓冲，全树**没有任何读者** |
| `debug` 级别 | 级别 3，所有 exporter 默认级别 1 → 进缓冲之前就被丢弃 |

结论：`info` 进了无人读的缓冲，`warn`/`error` 只在启动崩溃时被顺便打印。**写 `logger.debug` 和写注释是等效的。**

所以「退役信号」必须走一条真正能到达的通道。在本插件里那是 `lib/diagnostics.js`：一个有界环形缓冲，经 `ssh_workspace_status` 工具和面板 status 路由暴露。上游一修好，状态里就出现：

```
upstream workaround OBSOLETE: UPSTREAM-1-working-directory-isAbsolute — ...
```

设计上要注意两点：

- **事件流之外还要一个「当前状态」字段**。事件是时序的，会被后续事件挤出缓冲；而「我们的某个补丁该删了」这个问题必须**任何一次启动都能一眼回答**，不取决于有没有人看见那条事件。本插件的做法是 `upstreamWorkarounds` 数组（每次启动重建）+ `upstream` 事件（时序提示）并存。
- **正常状态不要写进环形缓冲**。`broken` 是每次启动的常态，逐个记录只会把真正重要的那条挤掉。只记 `fixed` 与 `unprobeable`。

### 7. 语义相反的测试，且失败信息自带解法

上游修好那天，那条「断言缺陷仍然存在」的测试会变红。而**红在这里的意思是「删掉我」，不是「修好我」**。

人的第一反应永远是「测试坏了，改一下」——这个动作会把退役信号永久消掉。所以这条断言必须自带防护，而且防护不能只有文件头注释：

- 失败信息本身要写清该删什么（`check()` 支持一个 `onFail` 参数，把删除清单打在被染红的那行下面）；
- 理由要写在**断言旁边**，不是模块顶部；
- 如果 CI 上有这条测试，失败信息就是唯一会被看到的东西。

本仓库的 `DELETE_THE_WORKAROUND` 常量就是干这个的：把 5 步删除清单直接印在红色的 FAIL 行下面。

## 四条反模式

| 反模式 | 为什么错 | 正确做法 |
| --- | --- | --- |
| 比对版本号 | 要求你预测尚未发生的发布，猜错两个方向都坏 | 探测行为 |
| `try { probe() } catch {}` | 把「探测失败」和「上游已修」压成同一个 `false`（或同一个 `true`） | 三态/六态，`unprobeable` 要告警 |
| 自动删除自己的代码 | 插件删不了自己的文件；而误删一个仍在旧版本承重的补丁，代价是所有人坏掉 | 自动停用 + 通知，删除由人做 |
| 只靠注释标「以后要删」 | 那不是机制 | 七件套 |

## 自我误判：为什么需要 `already` 状态

一个容易踩的坑：放宽过的 schema 自己也能接受探测值。所以第二次启动时，探测会看到「schema 接受 `ssh://`」，从而误判为「上游修好了」——**把补丁认成上游的修复**。

解法是给放宽版打一个私有的 `Symbol` 标记，探测时**先排除自己的产物**，再判断是否接受。`probeUpstream` 里那行 `if (candidates.some(isRelaxed)) return { state: PROBE.already }` 就是这个。

任何抄这套机制的人都必须带上它，否则退役判断从第二次启动开始就失效。

## 成本：这个模式不便宜

诚实地说清成本，否则它会被滥用：

本插件的 `UPSTREAM-1` 单实例的固定成本是 **约 500 行模块 + 两个测试套件（66 + 18 项断言）+ 三页文档**，对抗的是上游**一行**写法。

这个比例在本次是划算的，因为它的失效形态是「用户可见的、整体性的、报错指向错误的」。但它绝不意味着所有小补丁都该配这套东西。

**适用条件请和本文第一节的失效形态判断一起用**：只有补丁失效会造成用户可见的损坏时，才值得付这套成本。否则，一条带 issue 链接的注释就是合理答案。

## 本仓库的现状

| 项 | 状态 |
| --- | --- |
| 登记的补丁数 | **1**（`UPSTREAM-1-working-directory-isAbsolute`） |
| 探测状态 | 六态（`PROBE`），见 `lib/patch-projection.js` |
| 退役判据 | 接受 **且** 证明读了 `isAbsolute` 绑定（`lib/path-binding.js`） |
| 退役信号通道 | `ssh_workspace_status` 的 `upstreamWorkarounds` 字段 + `upstream` 事件 |
| 反向测试 | `tests/projection-real-smoke.mjs` 第一节（真实宿主 schema，红 = 删补丁） |
| 手工验证开关 | `DSH_SSH_WORKSPACE_DISABLE_UPSTREAM_WORKAROUNDS=1` |

**n = 1 的提醒**：这套模式目前只被一个实例验证过。把它当假设，不是当规律。等到第二个、第三个插件真正用过一次，再考虑把它固化成流程或 skill——那时候能知道哪些步骤是必需的、哪些只是这个例子的偶然产物。
